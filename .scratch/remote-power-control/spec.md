# ESP32-C3 电脑电源控制重构规格

- 状态：草案，待确认
- 流程阶段：Phase 2（规格编写）
- 范围：首个实现版本
- 任务跟踪：Local Markdown

## 问题说明

旧版 ESP32-C3 电脑电源控制项目混合了 ESPHome、Arduino 回退固件、未完成的 MQTT/云端试验和设备专属部署信息。它没有提供一条清晰、可测试、可恢复的远程控制链路，也未充分保证互联网或云端不可用时本地控制仍能工作。

重构系统必须安全、可观测地触发一次电源键短按，并确保云端不可用时本地控制仍可独立运行。设备收到命令不能被误报成电脑已经开机或关机。

## 方案概述

在独立 Git 仓库中开发 ESP-IDF/C++ 设备固件，以及使用 Node.js、TypeScript、Fastify 和 SQLite 的模块化云端单体服务。设备提供认证本地网页、USB 维护日志、局域网 Ping 可达性报告、主动 HTTPS 轮询、一次性配对和签名双分区 OTA。云端提供账号认证、设备配对、设备凭据管理、命令生命周期、诊断事件存储、OTA 元数据和审计 API。

首个实现阶段通过 API 和测试客户端验证设备与服务端控制链路。核心流程端到端验证通过前，不开发手机端 UI。

## 用户故事

1. 作为本地使用者，我可以通过局域网认证网页请求一次安全短按。
2. 作为本地使用者，即使云端或外网不可用，我仍可以控制设备。
3. 作为维护者，我可以通过 USB 查看设备实时日志。
4. 作为远程使用者，我可以登录云端，并通过服务端 API/测试客户端请求一次短按。
5. 作为远程使用者，我可以区分命令已接受、已执行、失败、过期与电脑电源状态。
6. 作为使用者，我可以分别查看设备在线状态和主机网络可达性，不把它们误认为电脑电源状态。
7. 作为管理员，我可以生成短时有效的一次性配对码并绑定设备。
8. 作为管理员，我可以撤销设备凭据；被撤销的设备必须重新配对。
9. 作为维护者，我可以在云端查看已脱敏的命令、轮询、认证、错误和 OTA 事件。
10. 作为维护者，我可以发布签名固件，并在新版本健康检查失败时自动回滚。
11. 作为使用者，我可以配置局域网 Ping 目标而不必重新编译固件。

## 功能需求

### 设备控制

- 正式固件使用 ESP-IDF/C++。
- GPIO1 是电源键输出，默认电平为 LOW。
- 一次短按是约 300 ms 的有界脉冲。
- 启动、复位和 OTA 流程不得产生脉冲。
- 执行器忙时拒绝新命令，不排队、不延长当前脉冲。
- 本地和云端请求经过同一执行器、校验和去重逻辑。
- 每条云端命令都有唯一 ID 和过期时间；设备端负责去重。
- 命令回执只说明脉冲执行结果，不说明电脑电源状态。

### 本地操作

- 本地网页使用独立于云端账号的本地凭据。
- 首次本地配置和恢复通过 USB 串口完成。
- 本地凭据保存在 ESP32 安全存储中。
- 外网或云端不可用时，本地网页仍可控制设备。
- USB 提供实时诊断日志和维护命令。
- Wi-Fi 初次设置或连接失败时提供受保护的配置 AP。

### 主机状态观察

- 首版电脑电源状态始终为 `unknown`。
- ESP32 对可配置目标执行局域网 Ping，只报告 `reachable`、`unreachable` 或 `unknown`。
- 不得将 Ping 结果转换为电脑 `on` 或 `off`。
- 后续 PWR-LED 光耦输入作为实际电源状态主检测；Ping 作为辅助确认。

### 云端服务

- 使用 Node.js、TypeScript 和 Fastify，模块化单体部署。
- 使用 SQLite，并通过仓储接口和迁移管理数据。
- 用户名/邮箱与密码登录；使用密码哈希、HTTPS 安全会话和登录限速。
- 首版单用户、单设备；数据模型不得妨碍未来扩展。
- 设备只通过主动 HTTPS API 轮询通信；不使用 MQTT，也不开放设备入站端口。
- 在线轮询基线为 5 秒，心跳基线为 30 秒。
- 每次轮询最多领取一条命令。
- 设备离线时立即拒绝命令，不排队、不在重连后补发。
- 命令具有有效期、唯一 ID 和可审计的状态变化。
- 使用短时有效的一次性配对码绑定设备，并签发独立设备凭据。
- 设备凭据被撤销后必须重新配对。
- 浏览器/API 客户端不得获得设备凭据。
- 云端保存命令结果、设备在线状态、主机可达性报告、配对、认证和错误事件。

### 诊断日志

- 设备通过 HTTPS 直接同步结构化关键事件。
- 云端不可达时仅使用有界 RAM 缓存；设备重启后允许丢失。
- 不在 Flash 上建立持久日志队列。
- USB 实时日志保留。
- 日志不得包含密码、配对码、长期凭据或完整认证头。
- 已认证用户可按设备和时间查询日志。

### OTA 与硬件基线

- 设备至少有 4 MB Flash。
- 仅接受签名固件镜像。
- 使用双 OTA 应用分区。
- 升级前检查目标硬件、版本、签名和镜像大小。
- 新固件首次启动须通过健康确认；失败时自动回滚。
- OTA 过程中不得触发电源键脉冲。
- 2 MB 设备不在支持范围内。
- 不预留大型设备文件系统或持久化日志队列。

### 部署

- 沿用现有主机、域名和 Cloudflare Tunnel。
- 新应用、SQLite 数据库、备份、凭据和部署配置与旧服务隔离。
- 公网只开放 HTTPS Web/API。
- 生产切换前须完成备份恢复验证并编写回滚步骤。

## 实现决策

- 独立仓库：`D:/PI/ESP32-C3-PC-POWER-NEXT`。
- `reference/` 下的旧项目资料仅供调查，不构成规范。
- 固件按职责拆分电源执行器、命令协议、本地认证/网页、Wi-Fi/配置、Ping、云端客户端、诊断和 OTA。
- 云端按职责拆分认证、配对/设备身份、命令服务、设备协议、持久化仓储、诊断、OTA 元数据和 HTTP 适配层。
- 只有命令服务可以创建、领取和完成电源命令。
- 仓储接口是数据存储替换边界；HTTPS 设备 API 和设备命令执行器是主要行为测试边界。
- 手机端 UI 不在首个实现阶段范围内。

## 测试决策

主要测试边界：

1. **设备命令执行器**：在无硬件环境测试脉冲时限、安全状态、忙时拒绝和重复 ID；在真实 4 MB 板卡验证脉冲和复位行为。
2. **云端命令服务**：使用测试 SQLite 验证授权、离线拒绝、过期、单次领取、幂等和命令生命周期。
3. **设备 HTTPS 协议**：使用模拟服务测试配对、认证、轮询/领取、回执、事件上传和重放拒绝；再对 Fastify 服务执行端到端测试。
4. **OTA**：验证分区布局、签名拒绝、镜像大小、健康确认和回滚；使用可用的模拟环境或真实硬件完成验证。
5. **本地/云端故障矩阵**：验证云端中断时本地仍能控制、恢复后不补发、RAM 事件缓存有界及 GPIO 安全状态。

验收证据包括可行范围内的自动化测试、`git diff --check`、构建/类型检查、API 契约测试和有记录的真实板卡冒烟测试。

## 不在范围内

- 首个实现阶段的手机端 UI。
- MQTT、消息 Broker 和微服务。
- 远程强制关机或长按。
- 根据 Ping 或命令回执推断电脑电源状态。
- 首个实现阶段的 PWR-LED 硬件接入。
- 多用户邀请、角色和多设备管理。
- 原生手机应用。
- 大型设备文件系统、Flash 持久化日志队列和离线命令队列。
- 更换现有主机或域名基础设施。

## 风险与待确认问题

- ESP32-C3 SuperMini 闪存容量和分区兼容性必须在目标硬件上实测。
- 需要针对 ESP-IDF 明确安全存储能力与恢复方式。
- HTTPS 信任策略和设备凭据轮换仍需威胁建模。
- 5 秒轮询需要做简单负载估算和限速设计。
- 云端或外网不可用时，本地网页认证及配置 AP 行为必须验证。
- 签名密钥保管与备份不能进入仓库。
- 精确 API Schema、数据库 Schema、日志保留策略和生产切换方式由 tickets 进一步落实。

## 成功标准

- 一块真实 4 MB ESP32-C3 可完成配置、配对和本地控制。
- 已配对设备可通过 HTTPS 连接测试服务，并对一条有效命令恰好执行一次短脉冲。
- 重复、过期、未授权和设备离线的命令都不会触发脉冲。
- 设备与云端日志可以定位命令和网络故障，且不会泄漏秘密。
- 签名 OTA 可成功升级；故意制造的不健康镜像会自动回滚。
- 云端不可用时本地控制不受影响。
- 后续手机端可直接使用已文档化且经过测试的 API，无需改变设备控制语义。
